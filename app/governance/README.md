# Governance

> **Parent:** [ARCHITECTURE.md](../docs/ARCHITECTURE.md) — platform layer model and component topology

## Purpose

The Governance component enforces who-can-do-what across every layer of the Universal Worker Platform. It implements an XACML-style policy decision architecture (PAP/PDP/PEP/PIP), embedding enforcement points at every platform layer — Gateway, Orchestrator, Worker Runtime, Memory, Tool Registry, and Infrastructure. No autonomous action proceeds without authorization, and every decision is immutably audit-logged.

## Contracts

### Implements

- **GovernanceContract**: The canonical governance interface exposed to the Worker Platform and Application layers. Covers authorization checks, approval gating, audit queries, resource limit enforcement, cost checks, and secret access control (see [GovernanceContract specification](../docs/ARCHITECTURE.md) Section 4.1).
- **Governance API v1**: REST API at `/governance/v1` with 7 endpoint groups: `check`, `approvals`, `audit`, `limits/check`, `costs/check`, `secrets/access`, `policies`.

### Depends On

- **Contracts** (`../contracts/`): `GovernanceContract` interface definition, `ContextContract` for attribute retrieval during policy evaluation.
- **Memory** (`../memory/`): Persists audit log entries, policy definitions, approval records, and quota state. Governance is a heavy writer to audit logs and policy stores.
- **Tool Registry** (`../tool-registry/`): Consults allowed-toolset per worker for tool invocation authorization.
- **Workspace Runtime** (`../workspace-runtime/`): Receives resource limits (cgroups, seccomp profiles) generated by governance for per-task enforcement.
- **Services** (`../services/`): Audit log storage (hot/cold layers), secret vault integration (Vault, AWS Secrets Manager).
- **Infrastructure** (`../infra/`): Network policy, filesystem quotas, and container sandbox configs are driven by governance rules.

### Exposes

- `POST /governance/v1/check` — Authorization decision for any platform action (allow | deny | pending_approval)
- `POST /governance/v1/limits/check` — Resource quota validation before task execution
- `POST /governance/v1/costs/check` — Cost budget validation against project/task budgets
- `POST /governance/v1/secrets/access` — Short-lived credential issuance with full audit trail
- `GET /governance/v1/audit` — Queryable, tamper-evident audit log with time/actor/action/resource filters
- `POST|PUT|GET|DELETE /governance/v1/approvals` — Approval lifecycle management
- `POST|PUT|GET|DELETE /governance/v1/policies` — Policy CRUD (admin only; deletes are deprecation, never removal)

## Concepts

- **PAP (Policy Administration Point)**: Administrative interface for creating, updating, versioning, and deprecating governance policies. Policies are stored as versioned YAML documents.
- **PDP (Policy Decision Point)**: Embedded decision engine in the Governance Service. Evaluates policies against an incoming action, returning `allow`, `deny`, or `pending_approval`. Consults the PIP for context attributes.
- **PEP (Policy Enforcement Point)**: Intercept points at every platform layer. Each PEP intercepts an action, calls the PDP, and enforces the result. Implemented as middleware (Gateway), pre-task checks (Orchestrator), cgroups/seccomp (Worker Runtime), access guards (Memory), invocation gates (Tool Registry), and network/filesystem policies (Infrastructure).
- **PIP (Policy Information Point)**: Provides contextual attributes to the PDP during evaluation — user attributes, resource state, task context, budget consumption, and trust scores. Backed by the Context Store and Memory Services.
- **RBAC (Role-Based Access Control)**: Six roles (`admin`, `operator`, `developer`, `auditor`, `worker`, `service`) each with scoped capabilities. Permissions follow deny-by-default with explicit deny overriding allow.
- **Resource URN**: `urn:uwp:{tenant}:{project}:{resource-type}:{resource-id}` — canonical identifier for every platform resource. Resource types: `task`, `context`, `worker`, `tool`, `secret`, `artifact`, `policy`, `infra`.
- **Approval Gate**: Triggered by configurable thresholds (cost, tool risk, resource scale-up, new worker registration, secret access, cross-tenant actions). Approval lifecycle: REQUEST → PENDING → APPROVED/DENIED/EXPIRED.
- **Audit Log**: Append-only, tamper-evident, cryptographically signed (Ed25519 hash chain) record of every authorization decision. 9 mandatory event categories with graduated retention (3yr–permanent). Queryable by time, actor, action, resource URN, event category, trace ID.
- **Defense in Depth**: Governance enforced independently at all 6 platform layers. A bypass at one layer does not compromise governance at others.

## Enforcement Architecture

### Per-Layer Enforcement Points

| Platform Layer | PEP Implementation | Checks Performed |
|---|---|---|
| **Gateway** | API middleware | AuthN (JWT/OAuth/OIDC validation), TLS termination, IP allowlist, rate limiting |
| **Orchestrator** | Pre-task check hook | AuthZ (permission check via PDP), resource quota validation, cost estimate check, approval gate evaluation |
| **Worker Runtime** | Container sandbox enforcement | cgroups v2 (CPU, memory limits), seccomp profile, AppArmor/SELinux, network namespace isolation, read-only rootfs, capability drop, image signature verification |
| **Memory** | Context access guard | Scope validation (task owns accessed context), encryption at rest, read/write access logging per domain |
| **Tool Registry** | Tool invocation guard | Tool allowlist check, per-tool rate limiting, input/output hash logging, duration tracking |
| **Infrastructure** | Network and filesystem policy | Egress allowlist (eBPF/iptables), storage quota (XFS project quotas), DNS restriction, process isolation |

### Policy Decision Flow

```
Actor → PEP (intercept) → PDP (evaluate policies) → PIP (fetch context/attributes)
                                 │
                    ┌────────────┼────────────┐
                    ▼            ▼            ▼
                  DENY         ALLOW     PENDING_APPROVAL
               (reject +     (execute +   (queue for
                audit log)    audit log)   approver review)
```

### Policy Definition Format

Policies are YAML documents with fields: `id`, `version`, `description`, `effect` (allow/deny), `conditions` (field-operator-value triples), `priority`, and `immutable` flag. See `arch-uwp-governance-model` in [ARCHITECTURE.md](../docs/ARCHITECTURE.md) for complete schema.

## Resource Limits

| Resource | Default Per-Task | Hard Maximum | Enforcement |
|---|---|---|---|
| CPU | 1 vCPU | 4 vCPU | cgroups v2 at container runtime |
| Memory | 512 MB | 4 GB | cgroups v2 at container runtime |
| Storage (scratch) | 1 GB | 10 GB | XFS project quotas / overlay size |
| Network egress | 100 MB | 1 GB | eBPF / iptables rate limiter |
| Execution time | 300s (5 min) | 3600s (1 hr) | Orchestrator (SIGALRM → SIGKILL) |
| Tool invocations | 50 | 500 | Governance API counter |
| Concurrent tasks | 1 | 10 | Orchestrator semaphore |
| API rate | 10 req/s | 100 req/s | Gateway token bucket |

Quota violations: soft limit → warning logged, action continues. Hard limit → task terminated, audit log records `resource:exceeded`. Repeated violations flag the worker for review.

## Cost Limits

Cost is attributed per task, project, and tenant. Enforcement runs at three stages:
- **Pre-flight**: Estimated cost checked against remaining budget. Reject if estimate exceeds remaining.
- **In-flight**: Running cost tracked. Soft-terminate (SIGTERM + 30s grace) if running cost exceeds 1.5× task budget.
- **Post-flight**: Actual cost calculated and deducted from project budget. Over-budget tasks flagged for review.

Default rates (configurable per tenant): CPU $0.00001/vCPU-second, Memory $0.000005/MB-second, Tool invocation tool-defined (default $0.0001/call), Network egress $0.01/GB.

## Security Boundaries

Six-layer defense architecture with enforcement at each boundary:

1. **Edge (Gateway)**: TLS 1.3+, AuthN (OIDC/OAuth/Passkeys/mTLS), rate limiting
2. **Orchestration**: PDP/PEP authorization, approval gating, quota enforcement
3. **Worker Sandbox**: Minimal base images with read-only rootfs, no host network, seccomp + AppArmor profiles, all capabilities dropped, no privileged mode
4. **Secrets**: External vault (HashiCorp Vault, AWS Secrets Manager, Doppler). Short-lived credential injection, never persisted to worker context. Referenced by URN only.
5. **Network**: Micro-segmentation — workers in isolated network namespaces, egress allowlist only, inter-worker communication disabled by default, DNS restricted to internal resolver
6. **Data**: Encryption everywhere — in-transit (TLS 1.3), at-rest (AES-256-GCM), memory contexts encrypted between invocations

## Implementation Guidance

### Getting Started

1. **Read the governance model contracts** in [ARCHITECTURE.md](../docs/ARCHITECTURE.md) — search for `arch-uwp-governance-model` for the full 12-section specification covering permissions, approvals, audit, resource limits, cost limits, security boundaries, enforcement architecture, and the Governance API contract.
2. **Understand the PAP → PDP → PEP → PIP flow** — this is the governance backbone. Every action in the platform flows through this pipeline.
3. **Implement the Governance API first** — the `/check` endpoint is the critical path. All other governance features (approvals, audit, limits, costs, secrets) build on the authorization check pipeline.

### Implementation Order

1. **Policy Decision Point (PDP)** — The core decision engine. Implement policy evaluation with condition matching (field-operator-value), deny-by-default, explicit deny override, and scope hierarchy.
2. **Policy Administration Point (PAP)** — CRUD for policies with versioning. Policies are immutable once created; new versions require new version IDs.
3. **Audit Writer** — Append-only, tamper-evident audit log. Each entry carries an Ed25519 signature chaining to the previous entry's hash. Implement hot storage (last 90 days, queryable) and cold archive.
4. **Governance API endpoints** — Implement all 7 endpoint groups (`check`, `approvals`, `audit`, `limits/check`, `costs/check`, `secrets/access`, `policies`).
5. **Policy Enforcement Points** — Instrument each platform layer with PEPs that intercept actions and call the PDP. Start with the Orchestrator PEP (highest leverage), then Gateway, Tool Registry, Memory, Worker Runtime, Infrastructure.
6. **Approval engine** — Lifecycle management (request/pending/approved/denied/expired), threshold evaluation, auto-approval policy matching, approver routing.
7. **Secret access control** — Integration with external vault providers, short-lived credential issuance, URN-based referencing.

### Key Design Decisions

- **PDP is embedded, not a separate service** — Minimizes latency on the authorization hot path. Every action requires a policy decision; remote PDP calls would bottleneck the platform.
- **PEPs are distributed, PDP is centralized** — Each layer enforces its own PEP (ensuring defense in depth), but all PEPs call the same PDP (ensuring consistent policy evaluation).
- **Audit log is the canonical record of truth** — Every governance decision (allow, deny, pending) is audit-logged. The audit log, not application logs, is the authoritative source for compliance and forensic analysis.
- **Secrets never stored in worker context** — Workers request secret injection with justification; governance validates, issues a short-lived wrapped token (e.g., Vault response-wrapping), and the token never persists beyond the tool invocation.
- **Policies are versioned YAML documents** — Human-readable, git-trackable, diffable. This supports infrastructure-as-code workflows where policies are reviewed in PRs before deployment.

### Testing Strategy

- **Unit tests**: Each PDP condition operator, policy priority resolution, deny-override logic, scope hierarchy resolution.
- **Integration tests**: Full PEP → PDP → PIP flow for each layer, with each decision outcome (allow, deny, pending).
- **E2E tests**: Complete task lifecycle with governance enforcement at every layer — submit task, pass authorization, enforce quota, complete, audit log verify.
- **Audit integrity tests**: Verify append-only property, hash chain continuity, tamper detection, query performance.
- **Security tests**: Attempted privilege escalation (worker requests admin action), container escape attempts (exceeded resource limits), secret exfiltration attempts (secret value in audit log).

### Non-Negotiable Constraints

1. No action bypasses the PDP — every action MUST be checked.
2. No audit log entry is mutable after write — append-only, forever.
3. No secret value appears in any log, audit entry, or worker context — URNs only.
4. Hard resource limits MUST terminate tasks, not throttle them — no partial degradation.
5. Container sandbox MUST drop all capabilities and add only required — never privileged mode.
6. All governance API responses MUST include the audit log ID — traceability from response to audit.

### Integration Points

| Integration | Direction | Description |
|---|---|---|
| Context Store (PIP) | Governance → Memory | PDP queries PIP for actor attributes, resource state, trust scores |
| Provider Registry | Governance → Contracts | PDP resolves which policies apply based on contract-to-resource mapping |
| Workspace Runtime | Governance → Workspace | Resource limits and seccomp profiles flow from governance to sandbox |
| Tool Registry | Governance → Tools | Tool invocation guard checks allowed-toolset per worker |
| Secret Vault | Governance → Services | Short-lived credential issuance via Vault/STS |
| Observability | Governance → Infra | Audit log streams to SIEM/webhook; Prometheus metrics for PDP latency, approval queue depth |
